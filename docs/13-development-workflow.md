# 开发工作流

## 1. 规格驱动

每个功能先明确：用户故事、文件影响、API 契约、错误码、验收标准和测试。不要从 UI 随意开始并在后端临时补逻辑。

## 2. 垂直切片

优先完成可运行的小闭环，例如“创建项目”：

1. JSON Schema；
2. Repository；
3. Service；
4. API；
5. 前端表单和列表；
6. 测试；
7. 文档。

避免先写完整后端再一次性接前端。

## 3. Codex 协作节奏

- 用 `.codex-prompts/prompt.md` 启动总任务；
- 根目录的 `AGENTS.md` 保存长期不变规则；
- `.codex-prompts/PLANS.md` 保存里程碑和状态；
- `.codex-prompts/TASKS.md` 保存当前迭代任务；
- 每次给 Codex 一个明确阶段、验收条件和停止点；
- 复杂任务可拆给子代理，但需要主代理统一检查；
- 同一错误重复出现时，把具体规则补入根目录的 `AGENTS.md`。

## 4. 代码审查清单

- 是否触碰源 PDF？
- 是否绕过 repository 直接写文件？
- 是否存在任意路径参数？
- 是否使用原子写和 revision？
- 是否更新 schema/API/错误码？
- 是否有失败路径测试？
- UI 是否准确说明影响？
- 是否引入超出当前阶段的依赖和功能？

## 5. ADR

下列变化必须写 ADR：

- 权威数据格式变化；
- 引入数据库或远程服务（通常应拒绝或推迟）；
- PDF 导入语义变化；
- 新的认证/部署模式；
- API 版本策略变化；
- AI 服务商和上传策略。

## 6. 版本和迁移

- 代码采用语义化版本；
- 文件 schema 独立版本；
- 迁移必须可测试、可预览；
- 不支持降级写回新版本文件；
- 发布说明列出数据格式变化。
